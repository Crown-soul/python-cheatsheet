Git 基本流程

從建立倉庫到同步上 GitHub，一個人做專案也用得上的完整流程。每個單元都是同一個順序：一句話重點 → 白話解釋 → 可以照打的指令 → 執行結果 → 容易踩的坑。不用背，照著打一次就懂了。

14 個單元 約 35 分鐘 範圍：init / status / add / diff / commit / log / .gitignore / restore / amend / revert / clone / push / pull（不含分支、衝突的解法）

要背的只有這幾個，其他都用查的

14 個單元裡，每天都會用到的只有這兩組指令。其他 12 個是「出事的時候回來查」，平常不會碰。
這一塊只有兩項，不是漏寫——真正要背的就這麼少。

01存檔的三步
$ git add .
$ git commit -m "做了什麼"
$ git push

順序不能換：先放進暫存區、再存成一個版本、最後才上傳。-m 後面一定要有訊息，少了它 Git 會跳出編輯器。

02隨時問現在在哪一步
$ git status

忘記做到哪、不確定改了什麼、不知道下一步該打什麼，就打這個。它會把現在的狀態跟建議的下一步都印出來。不確定的時候先打它，不要猜。

這些放心去查，不用背
restore / amend / revert 的差別跟參數、.gitignore 的寫法、clone 跟 pull 的細節、push 被拒絕怎麼處理。這些都是出狀況才會用到，查得到就好。
自我測試
把這個資料夾改一個字，然後不看筆記，把改動存成一個版本推上去。三行指令打得完就過關。
這份筆記怎麼用
第一輪只讀每個單元的「一句話重點」和橘色的坑，跳過指令，十分鐘把整個流程建起來。第二輪讀指令，但用手遮住下面的「輸出」，先自己講出畫面會出現什麼再對答案——猜錯的地方就是你要補的地方。第三輪關掉這頁，開一個測試資料夾把練習題做一遍，卡住才回來查。Git 的指令看十遍不如自己打壞一次再救回來。
CH 1 · 建立一個倉庫
01

版本控制在做什麼

Git 是幫專案存很多個「存檔點」的工具，每個存檔點都能回得去。

寫程式的過程常常會改壞東西、想不起來昨天改了什麼、或是想比較兩個版本差在哪。Git 每次存檔（commit）都會記下當時整個專案的樣子，之後隨時能回去看、能比較、能還原。不用 Git，「復原」只能靠自己複製一份 專案_舊版、專案_最終版、專案_真的最終版 這種資料夾。Git 跟 GitHub 是兩個東西，單元 12 會分清楚。

02

git init：把資料夾變成倉庫

git init 是跟 Git 說「從這裡開始，幫我記錄以後的每個改動」。

在一個資料夾裡執行一次 git init，這個資料夾就變成一個 Git 倉庫（repository），底下會多一個藏起來的 .git 資料夾，所有歷史紀錄都存在那裡面。整個專案只需要在最上層的資料夾做一次，不要每個子資料夾都各做一次。

終端機 
$ git init -b main
Initialized empty Git repository in /Users/你/Desktop/demo/.git/
容易踩的坑
不要在使用者根目錄（像 ~/Desktop）直接執行 git init，會把整個桌面都變成追蹤範圍。先 cd 進專案自己的資料夾再 init。
03

三個區域：工作目錄、暫存區、倉庫

改動要先放進暫存區，才能存進倉庫，中間隔著你自己按下的確認動作。

工作目錄
你電腦上看到的檔案
正在改的東西，Git 還沒開始管它。
暫存區
git add 之後放的地方
打包好、準備存檔，但還沒真的存下去。
倉庫
git commit 之後存的地方
正式存檔，變成一個回得去的版本。

後面兩個單元的 git add、git commit 就是分別對應這三個區域之間的兩個動作，先搞懂這張圖，後面的指令就不是死背了。

CH 2 · 記錄每一次改變
04

git status：現在是什麼狀態

不確定現在改了什麼、進度到哪，永遠先打 git status。

這個指令只是「看」，不會改變任何東西，隨時打都安全。養成每做一步就看一次的習慣，比事後靠記憶猜好用。

終端機 
$ git status
On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	hello.py
	memo.txt

nothing added to commit but untracked files present (use "git add" to track)
  • Untracked filesGit 還沒開始追蹤的新檔案，兩個都是剛建立、還沒 add 過。
  • No commits yet這個倉庫還沒存過任何一個版本，是全新的。
05

git add：放進暫存區

git add 不是存檔，是把改動放進「準備存檔」的箱子裡。

終端機 
$ git add hello.py
$ git status --short
A  hello.py
?? memo.txt
  • Ahello.py 已經放進暫存區，準備存檔。
  • ??memo.txt 還沒被 add，還停在工作目錄。
容易踩的坑
習慣打 git add . 會把整個資料夾的東西一次全部加進去，包含不小心留在裡面的密碼、大檔案。剛開始學，一個一個檔名點名加比較安全，或是先寫好 .gitignore（單元 09）再用 .。
06

git commit：正式存一個版本

git commit 才是真的存檔，而且一定要附一句話說這次改了什麼。

終端機 
$ git commit -m "Add hello.py"
$ git log --oneline
3ac9023 Add hello.py

訊息寫這次改了什麼，讓半年後的自己看得懂。一句話，結尾不用句號，中文英文都可以。

建議
不建議
新增變數與判斷式講義
update
修正 f-string 範例的錯字
修改
目錄頁加上 Git 筆記的連結
fix 2
容易踩的坑
commit 訊息不要寫 "update"、"fix" 這種看不出內容的話。半年後回頭找是哪一次改壞的，這句話是你唯一的線索。寫清楚「這次做了什麼」，不用寫「為什麼」。
07

git log：看歷史

git log --oneline 一行一個版本，新的在最上面。

終端機 
$ git log --oneline
679e158 Print a greeting twice
3ac9023 Add hello.py
  • 679e158每一行最前面這串英數字是這個版本的代號，之後要回到某個版本、或跟別人講「就是這一次改的」，靠這串代號指認。
08

git diff：看改了什麼

git diff 一行一行列出改了什麼：前面有 + 的是新增，有 - 的是刪掉。

commit 之前先跑一次，確認要存的內容就是你以為的內容。它跟 git status 一樣只看不改，隨時可以打。

終端機
$ git status --short
 M hello.py
?? memo.txt
$ git diff
diff --git a/hello.py b/hello.py
index 2f9a147..d4c2dc5 100644
--- a/hello.py
+++ b/hello.py
@@ -1 +1,2 @@
 print("Hello")
+print("Hello")
  • --- / +++--- 是改之前的版本，+++ 是改之後的版本。
  • @@ -1 +1,2 @@這一段改動在檔案的哪幾行：改之前從第 1 行起 1 行，改之後從第 1 行起 2 行。
  • +print("Hello")前面有 + 的行是新增的。沒有 + 或 - 的行沒動，列出來給你看前後文。

git diff 只看還沒 add 的改動。add 之後它就什麼都不印，要加 --staged 才看得到：

終端機
$ git add hello.py
$ git diff
$ git diff --staged
diff --git a/hello.py b/hello.py
index 2f9a147..d4c2dc5 100644
--- a/hello.py
+++ b/hello.py
@@ -1 +1,2 @@
 print("Hello")
+print("Hello")
  • git diff只看還沒 add 的改動。上面 add 之後它什麼都沒印。
  • --staged看已經 add、還沒 commit 的改動，下一個 commit 會存進去的內容就是這些。
容易踩的坑
git diff 什麼都沒印，不代表沒有改動：改動可能已經 add 了。用 git diff --staged，或是直接看 git status。
改動很多的時候，畫面會停在最下面的 : 或 (END)，按 q 離開，見附錄「指令卡住了怎麼辦」。
CH 3 · 忽略與復原
09

.gitignore：不想被記錄的檔案

把不想讓 Git 管的檔案名稱寫進 .gitignore，它們就不會再出現在 git status 裡。

.gitignore 
__pycache__/
*.log
memo.txt
輸出 git status --short 只剩 M hello.py 跟 ?? .gitignore，memo.txt 不再出現
容易踩的坑
.gitignore 只對「還沒被追蹤過」的檔案有效。如果一個檔案已經被 git add 或 git commit 過，寫進 .gitignore 也沒用，Git 還是會繼續追蹤它，要先用 git rm --cached 檔名 把它從追蹤清單移除。
容易踩的坑
密碼、API 金鑰、token 不能進 commit。倉庫如果是公開的，push 之後任何人都看得到。事後把檔案刪掉再 commit 也沒用，歷史紀錄裡仍然留著。做法是一開始就把檔名寫進 .gitignore，例如 .env、tts-key.txt。
金鑰已經 push 出去的話，要當成外洩處理：到發行金鑰的服務把它作廢，換一把新的。
10

git restore：反悔怎麼辦

改壞了、想變回上一次存檔的樣子，用 git restore 檔名，還沒 commit 的改動會直接消失。

終端機 
$ git status --short
 M hello.py
?? .gitignore
$ git restore hello.py
$ git status --short
?? .gitignore
  • restore 前後M hello.py 那行消失了，代表 hello.py 已經變回上一次 commit 時的樣子，剛才寫的東西真的不見了。

add 錯了檔案，想把它從暫存區拿回來，用 git restore --staged 檔名：

終端機
$ git add memo.txt
$ git status --short
A  memo.txt
$ git restore --staged memo.txt
$ git status --short
?? memo.txt
  • A → ??memo.txt 從「已放進暫存區」變回「還沒被 add」，檔案內容沒動。
容易踩的坑
git restore 是真的把還沒 commit 的修改刪掉，刪掉就找不回來了。先用 git status 或 git diff 確認真的要丟掉這個檔案的改動，不確定就先別動。
11

git commit --amend 與 git revert：commit 之後反悔

已經 commit 的東西不會消失：訊息寫錯用 --amend 改，整次改動想撤銷用 revert。

這兩個都是「已經 commit」之後的反悔，跟單元 10 的 git restore（還沒 commit）不一樣。先看訊息寫錯的情況：

終端機
$ git log --oneline
2a12348 Add helo.py
$ git commit --amend -m "Add hello.py"
[main 150a852] Add hello.py
 Date: Sun Sep 20 22:47:30 2026 +0800
 1 file changed, 1 insertion(+)
 create mode 100644 hello.py
$ git log --oneline
150a852 Add hello.py
  • 2a12348 → 150a852commit 的代號變了。--amend 是把最後一個 commit 換成新的，不是多加一個，所以 log 裡仍然只有一行。
  • 只能改最後一個--amend 只動最近一次 commit，更早的改不了。

想撤銷更早的某次改動，用 git revert。它新增一個反向的 commit，把那次的改動抵銷掉：

終端機
$ git log --oneline
79d0ffe Add debug print
9ffce54 Print a greeting twice
150a852 Add hello.py
$ git revert --no-edit 79d0ffe
[main d808f64] Revert "Add debug print"
 Date: Sun Sep 20 22:47:30 2026 +0800
 1 file changed, 1 deletion(-)
$ git log --oneline
d808f64 Revert "Add debug print"
79d0ffe Add debug print
9ffce54 Print a greeting twice
150a852 Add hello.py
  • 79d0ffe要撤銷哪一次，用 git log --oneline 查編號。
  • Revert "..."新增的反向 commit。Add debug print 那一行仍然在歷史裡，沒有被改寫。
  • --no-edit不加的話，Git 會開編輯器讓你確認說明；加了就直接用預設說明。編輯器的離開方式見附錄「指令卡住了怎麼辦」。

整理一下，不同的狀況用不同的指令：

狀況
指令
注意
改壞了檔案，還沒 add
git restore 檔名
改動會消失，救不回來
add 錯了檔案
git restore --staged 檔名
檔案內容不變，取消暫存的紀錄
commit 訊息寫錯，還沒 push
git commit --amend -m "新說明"
只能改最後一個 commit
已經 push，想撤銷某次 commit
git revert --no-edit 編號
新增一個反向的 commit，舊的歷史不動。編號用 git log --oneline 查
容易踩的坑
已經 push 的 commit 不要用 --amend 改。本機的歷史改了，跟 GitHub 上的對不起來，之後 push 會被拒絕，要用 --force 才推得上去，而 --force 是附錄列的危險指令。已經 push 的用 revert。
commit 過的內容幾乎找得回來。會弄丟的，是還沒 commit 的改動。
CH 4 · 跟 GitHub 同步
12

GitHub 與 remote：連到雲端的倉庫

GitHub 是放 Git 專案的網站。Git 在你的電腦上，GitHub 在網路上，兩邊靠 push 和 pull 同步。

到目前為止，三個區域都在你的電腦裡。加上 GitHub，資料的流向多了最後一站：

資料的流向
工作目錄    你改檔案的地方
    ↓  git add
暫存區      這次要存哪些檔案
    ↓  git commit
本機倉庫    存檔點記在你的電腦裡
    ↓  git push
GitHub      雲端，網站和別人看到的版本

GitHub 上的那份倉庫叫「遠端」（remote），預設的代號是 origin。要跟它連起來有兩種情況：

  • cloneGitHub 上已經有倉庫：git clone 網址，把它複製一份到你的電腦。
  • remote add電腦上先有倉庫（像單元 02 的 git init）：git remote add origin 網址，告訴 Git 遠端在哪。

這份筆記裡的 https://github.com/你/demo.git 是示範用的網址，換成你自己在 GitHub 上建的倉庫網址。連好之後用 git remote -v 檢查：

終端機
$ git remote add origin https://github.com/你/demo.git
$ git remote -v
origin	https://github.com/你/demo.git (fetch)
origin	https://github.com/你/demo.git (push)
  • (fetch) / (push)fetch 是下載，push 是上傳。兩個網址通常一樣。
容易踩的坑
改了檔案、存了檔、上傳了，是三件事。沒 commit 的改動最容易弄丟；commit 了但沒 push，內容只在你的電腦上，GitHub 上看不到。
13

git push 與 git pull：上傳與下載

git push 把本機的 commit 傳上 GitHub，git pull 把 GitHub 上的新 commit 抓回本機。

第一次 push 要多加 -u origin main，告訴 Git「本機的 main 對應 GitHub 的 main」。之後直接打 git push 就好。

終端機
$ git push -u origin main
To https://github.com/你/demo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
  • [new branch]GitHub 上原本沒有 main，這次建立了。之後的 push 會顯示成 舊代號..新代號 main -> main。
  • up to date本機的 main 跟 GitHub 上的一樣新，沒有落後，也沒有多出來的 commit。

在網頁上或另一台電腦改過、push 到 GitHub 之後，本機用 git pull 把新的 commit 抓下來：

終端機
$ git pull
From https://github.com/你/demo
   af09164..83dbe61  main       -> origin/main
Updating af09164..83dbe61
Fast-forward
 hello.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
$ git log --oneline
83dbe61 Edit greeting on the web
af09164 Add hello.py
  • Fast-forward本機沒有新的 commit，Git 直接把 GitHub 上的新 commit 接在後面。
  • af09164..83dbe61本機從 af09164 更新到 83dbe61。

上傳和下載的時候，畫面最前面還會跑幾行進度（像 Enumerating objects），跟有沒有成功無關，這份筆記省略。

容易踩的坑
git push 只送 commit。push 之前先跑 git status，確認想上傳的改動都 commit 了。
14

push 被拒絕：先合併再上傳

push 出現 rejected 或 fetch first，代表 GitHub 上有你本機沒有的 commit。先把它們合併進來，再 push。

常見原因是在網頁或另一台電腦上改過，本機不知道。下面的例子是兩邊各自 commit 了不同的檔案：

終端機
$ git push
To https://github.com/你/demo.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/你/demo.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally. This is usually caused by another repository pushing to
hint: the same ref. If you want to integrate the remote changes, use
hint: 'git pull' before pushing again.
hint: See the 'Note about fast-forwards' in 'git push --help' for details.
  • [rejected]GitHub 上有你沒有的 commit，這次上傳被擋下來，什麼都沒有傳出去。
  • hint:Git 給的建議，先讀。

建議說要用 git pull，但直接打會失敗：

終端機
$ git pull
From https://github.com/你/demo
   83dbe61..9faf453  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
hint:
hint: You can replace "git config" with "git config --global" to set a default
hint: preference for all repositories. You can also pass --rebase, --no-rebase,
hint: or --ff-only on the command line to override the configured default per
hint: invocation.
fatal: Need to specify how to reconcile divergent branches.
  • divergent分岔了：GitHub 和本機各自有對方沒有的 commit。
  • reconcileGit 不替你決定怎麼合起來，要你選一種。最直觀的是合併（merge），加上 --no-rebase。

合併之後再 push，就送得上去了：

終端機
$ git pull --no-rebase --no-edit
Merge made by the 'ort' strategy.
 web.py | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 web.py
$ git push
To https://github.com/你/demo.git
   9faf453..d79d469  main -> main
$ git log --oneline
d79d469 Merge branch 'main' of https://github.com/你/demo
fc6e811 Add local.py
9faf453 Add web.py
83dbe61 Edit greeting on the web
af09164 Add hello.py
  • --no-rebase用合併的方式把 GitHub 上的 commit 併進來。
  • --no-edit合併會產生一個新的 commit，這個旗標讓它直接用預設說明，不開編輯器。
  • Merge branch最上面那個 commit 是 Git 產生的合併紀錄，把 Add web.py 和 Add local.py 兩邊接在一起。

每次都加旗標很麻煩，可以設定一次，以後 git pull 就照合併的方式做（這個指令沒有輸出）：

終端機
$ git config --global pull.rebase false

pull 之後如果出現 CONFLICT，代表同一處兩邊都改了，Git 沒辦法決定留哪一邊：

終端機
$ git pull --no-rebase --no-edit
From https://github.com/你/demo
   d79d469..d61bcd2  main       -> origin/main
Auto-merging hello.py
CONFLICT (content): Merge conflict in hello.py
Automatic merge failed; fix conflicts and then commit the result.
$ git status --short
UU hello.py
$ git merge --abort
$ git status --short
  • UU這個檔案兩邊都改了，還沒處理。
  • --abort退回 pull 之前的狀態，檔案回到原樣。
容易踩的坑
出現 CONFLICT 的時候，停下來看訊息，不要急著改檔案。這份筆記不教怎麼解衝突：先 git merge --abort 退回原狀，再找懂的人一起看。
附錄

指令卡住了怎麼辦

出現一個滿是 ~ 的畫面Git 開了文字編輯器（預設多半是 vim），要你寫說明。按 i 開始打字，寫完按 Esc，輸入 :wq 再按 Enter，存檔離開。git revert、git pull 的合併說明已經有預設文字，直接 Esc、:wq 就行。
畫面停在 : 或 (END)，打指令沒反應輸出太長，Git 用分頁的方式顯示（git log、git diff 常見）。按 q 離開，空白鍵往下翻一頁。

git commit 沒寫說明就離開編輯器，會看到這一行，代表這次 commit 被中止了，重打一次並且加上 -m：

終端機
$ git commit
Aborting commit due to empty commit message.

怎麼讀錯誤訊息

Git 的錯誤訊息很長，先照下面三個順序看，多數時候不用讀完：

從最後幾行看起error: 或 fatal: 開頭的行是結論。error 是這次指令沒成功，fatal 是指令直接中止。
再讀 hint:hint: 開頭的行是 Git 給的建議，常常直接寫了下一步要打什麼。
跳過 To 和 FromTo 網址、From 網址 是告訴你連到哪一個倉庫，出錯時先跳過。

範例看 單元 14：先看到 rejected，讀 hint: 得知要 git pull；pull 之後換成 fatal:，再讀 hint: 選一種合併方式。

危險指令

下面三個指令會刪東西或覆蓋東西，跑之前要知道它在做什麼。

git push --force用本機的版本覆蓋 GitHub，GitHub 上別人的 commit 會消失。
git reset --hard丟掉所有還沒 commit 的改動，救不回來。
git clean -f刪掉所有沒被 Git 追蹤的檔案，救不回來。
注意
在網路上看到含這幾個字的指令，先別複製去跑。跑 git status，把畫面貼給懂的人看。

名詞小辭典

repository（repo）
專案資料夾，連同它所有的歷史紀錄。
commit
一個存檔點，也指「存檔」這個動作。
add
把檔案放進暫存區，決定這次 commit 包含哪些。
push
把本機的 commit 傳到 GitHub。
pull
把 GitHub 上的新 commit 抓回本機。
clone
把 GitHub 上的 repo 複製一份到本機。
branch
一條獨立的存檔線，主線預設叫 main。這份筆記沒教怎麼開新的。
remote / origin
GitHub 上那份 repo 的代號，origin 是預設的名字。
.gitignore
列出 Git 不要追蹤的檔案。
練習題

前七題各自對應前面幾個單元，最後一題把單元 01～11 的流程串起來，是這份筆記的大魔王題。每題都附「預期輸出」，自己跑完可以對答案。想看做法，寫完再點開「參考解答」。練習 7 需要一個 GitHub 帳號。

練習 1

建立第一個倉庫

新建一個空資料夾，cd 進去，執行 git init -b main，再打一次 git status 看看。

預期輸出 git status 會顯示「On branch main」跟「No commits yet」，沒有任何檔案列出來（因為資料夾裡還沒有東西）
參考解答（先自己寫，再點開對照）
終端機
$ git init -b main
Initialized empty Git repository in /Users/你/Desktop/demo/.git/
$ git status
On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

git status 的第二行是 No commits yet，因為資料夾裡還沒有任何檔案，所以沒有列出檔案。

練習 2

建立檔案並加進暫存區

在練習 1 的資料夾裡新增一個 notes.txt，寫幾個字進去，用 git add notes.txt 加進暫存區，再用 git status --short 確認。

預期輸出 git status --short 顯示 A notes.txt
參考解答（先自己寫，再點開對照）
終端機
$ echo "第一行" > notes.txt
$ git add notes.txt
$ git status --short
A  notes.txt

A 代表 notes.txt 已經放進暫存區。

練習 3

存第一個版本

把練習 2 加進暫存區的東西 commit 掉，訊息寫「Add notes.txt」，再用 git log --oneline 看一次歷史。

預期輸出 git log --oneline 顯示一行：一串英數字代號 + Add notes.txt
參考解答（先自己寫，再點開對照）
終端機
$ git commit -m "Add notes.txt"
[main (root-commit) 1d2f378] Add notes.txt
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt
$ git log --oneline
1d2f378 Add notes.txt

每個人的代號（1d2f378）不會一樣，訊息對就好。

練習 4

忽略一個檔案

新增一個 secret.log（假裝是不想被記錄的檔案），寫一個 .gitignore，裡面加一行 *.log，用 git status --short 確認 secret.log 有沒有出現。

預期輸出 git status --short 只看到 ?? .gitignore，secret.log 不會出現
參考解答（先自己寫，再點開對照）
終端機
$ echo "password=abc" > secret.log
$ echo "*.log" > .gitignore
$ git status --short
?? .gitignore

notes.txt 在練習 3 已經 commit 過，所以不會出現。secret.log 被 *.log 擋掉，清單裡只剩 .gitignore 這個還沒 add 的新檔案。

練習 5

看差異

在練習 4 的 notes.txt 再加一行，先用 git diff 看，再 git add notes.txt，之後分別用 git diff 跟 git diff --staged 各看一次。

預期輸出第一次 git diff 列出新增的那一行，前面有 +。git add 之後，git diff 什麼都不印，git diff --staged 才列出同樣的內容。
參考解答（先自己寫，再點開對照）
終端機
$ echo "第二行" >> notes.txt
$ git diff
diff --git a/notes.txt b/notes.txt
index 468d803..d2c1cb5 100644
--- a/notes.txt
+++ b/notes.txt
@@ -1 +1,2 @@
 第一行
+第二行
$ git add notes.txt
$ git diff
$ git diff --staged
diff --git a/notes.txt b/notes.txt
index 468d803..d2c1cb5 100644
--- a/notes.txt
+++ b/notes.txt
@@ -1 +1,2 @@
 第一行
+第二行

以 notes.txt 原本只有「第一行」為例。+第二行 就是新增的那一行。

練習 6

改 commit 訊息

把 notes.txt 改一下、add、commit，訊息故意寫成 Updte notes（錯字）。想辦法把訊息改成 Update notes，而且不要多出一個新的 commit。

預期輸出git log --oneline 最上面一行的訊息是 Update notes，Updte notes 那一行不會另外出現在清單裡。
參考解答（先自己寫，再點開對照）
終端機
$ git commit -m "Updte notes"
[main 211646a] Updte notes
 1 file changed, 1 insertion(+)
$ git log --oneline
211646a Updte notes
17945fd Ignore log files
1d2f378 Add notes.txt
$ git commit --amend -m "Update notes"
[main b010af4] Update notes
 Date: Sun Sep 20 22:48:09 2026 +0800
 1 file changed, 1 insertion(+)
$ git log --oneline
b010af4 Update notes
17945fd Ignore log files
1d2f378 Add notes.txt

--amend 換掉的是最後一個 commit，所以代號從 211646a 變成 b010af4，log 裡沒有多一行。

練習 7

推上 GitHub

在 GitHub 網頁上建一個空的倉庫（不要勾選加 README），用網頁給的網址，把練習 1～6 的資料夾連上去，然後 push。第一次 push 會要你登入，照畫面指示做，登入的細節這份筆記不教。

預期輸出push 的最後一行是 branch 'main' set up to track 'origin/main'.，接著 git status 顯示 Your branch is up to date with 'origin/main'.
參考解答（先自己寫，再點開對照）
終端機
$ git remote add origin https://github.com/你/demo.git
$ git remote -v
origin	https://github.com/你/demo.git (fetch)
origin	https://github.com/你/demo.git (push)
$ git push -u origin main
To https://github.com/你/demo.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git status
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean

網址換成你自己的倉庫。-u 只有第一次 push 要加。

大魔王

從零開始跑完整套流程

新建一個資料夾，一次用到這份筆記教的每一件事：

01 git init -b main，建立倉庫。
02 建立兩個檔案：main.py（隨便寫幾行）跟 debug.log（假裝是產生出來的紀錄檔）。
03 寫一個 .gitignore，排除 debug.log。
04 把 main.py 跟 .gitignore add 起來，commit 一次，訊息寫「Initial commit」。
05 修改 main.py 隨便加一行，add、commit 第二次，訊息寫清楚這次改了什麼。
06 再改一次 main.py，這次改完反悔，用 git restore 復原，最後用 git log --oneline 確認整個過程只留下兩個 commit，debug.log 從頭到尾沒被追蹤過。
大魔王提示
.gitignore 要在 debug.log 被 add 之前寫好，順序顛倒的話單元 09 的坑會直接發生在你身上。
第 6 步的 git restore 只能救回「還沒 commit」的改動。如果不小心先 commit 了才想反悔，git restore 不是對的指令，已經 commit 的東西要用單元 11 的 git revert。
結束時 git log --oneline 應該剛好兩行，不多不少；如果變成三行，代表某一步 commit 了不該 commit 的東西。
參考解答（先自己寫，再點開對照）
終端機
$ git init -b main
Initialized empty Git repository in /Users/你/Desktop/demo/.git/
$ echo "print(1)" > main.py
$ echo "log line" > debug.log
$ echo "debug.log" > .gitignore
$ git status --short
?? .gitignore
?? main.py
$ git add main.py .gitignore
$ git commit -m "Initial commit"
[main (root-commit) 0edd7df] Initial commit
 2 files changed, 2 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 main.py
$ echo "print(2)" >> main.py
$ git add main.py
$ git commit -m "Print a second line"
[main 056a02e] Print a second line
 1 file changed, 1 insertion(+)
$ echo "print(3)" >> main.py
$ git status --short
 M main.py
$ git restore main.py
$ git status --short
$ git log --oneline
056a02e Print a second line
0edd7df Initial commit

.gitignore 先寫好再 add，所以 debug.log 從頭到尾沒有出現在 git status --short 的清單裡。第 6 步 restore 之前是 M main.py，之後清單變空的，最後 git log --oneline 剛好兩行。
