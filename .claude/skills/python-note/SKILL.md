# 課程筆記產生器

這個 skill 是把既有筆記（變數與判斷式、迴圈、Git 基本流程）在設計上、文字上反覆調校出來的規則，整理成可以重複套用到新主題的模板，也可以套用到 Python 以外的科目。目標是：**新主題的筆記，排版跟語氣要跟現有的一模一樣**，換內容不換風格。

版本紀錄見 `CHANGELOG.md`。

## 先判斷這次任務屬於哪一種，再決定要讀哪些檔案

| 任務 | 讀這些檔案 |
|---|---|
| 產生新筆記 / 幫既有筆記加練習題大魔王 | `references/design-system.md` + `references/writing-style.md`，教材是雜亂原始素材的話再加 `references/source-material.md` |
| 把兩份以上既有的筆記合併成一份 | `references/source-material.md`「合併既有筆記」一節 + `references/design-system.md` |
| 只是局部修字、修 bug、加一兩個小區塊 | 只讀跟那個區塊有關的部分，不用整份讀完 |
| 學生貼程式碼問「這樣對嗎 / 我錯在哪」 | `references/review-workflow.md` |
| 純粹聊筆記以外的問題（環境操作、觀念問答） | 不用讀模板，直接回答；如果牽涉到「程式卡住」這類問題，答完可以問要不要順手補進附錄 |

不要每次任務都把四份參考文件整份讀完——批改程式碼用不到色票，修一個錯字用不到批改流程。看任務類型抓對應的檔案。

## 什麼時候要先問，什麼時候直接做

**要做新筆記、或範圍大幅擴充時**，先確認這幾件事，一次問清楚，不要做到一半才發現方向錯了：

1. **主題範圍**：這次要涵蓋哪些具體觀念？如果使用者是丟雜亂原始教材過來，範圍就是跑完 `references/source-material.md` 整理流程之後那份觀念清單，跟使用者確認過章節切法再開始寫。
2. **要不要附練習題／大魔王題**：預設不主動加，除非使用者要求。
3. **練習題要不要附答案／執行結果**：預設**不附**，讓學生自己驗證；使用者明確說「我要答案」「補上答案」，才用 `design-system.md` 的「參考解答」元件補進同一個檔案，解答裡的程式或指令一樣要實際跑過（實際發生過的流程：先給題目、學生自己寫、寫完才補解答）。
4. **輸出檔名與位置**：沒說的話，用該主題的英文當檔名放在根目錄（例如 `loops.html`），不要用中文檔名；如果目錄頁（`index.html`）已存在，記得同步加一張卡片，並在新筆記的 header 加回目錄的連結。

**局部修改、修字、修 bug、加一兩個小區塊**這種範圍明確的小改動，不用每次都照上面四點問一輪——直接做，做完再回報改了哪裡。只有真的看不出使用者要什麼的時候才問。

## 生成完成後的檢查清單

生成或修改完一份筆記，依序做完這幾件事再交給使用者：

1. **自動檢查（hook）**：`.claude/settings.json` 設了 PostToolUse hook，每次用 Write / Edit 改 `.html`，都會跑 `.claude/hooks/check-html.py`，檢查四件事：標籤開合數量、殘留的 Markdown 反引號（寫作時容易手滑打 `` `code` `` 而不是 `<code>`，HTML 不會轉譯，會直接顯示在頁面上）、內部連結與 `#錨點` 指不指得到、`style` 屬性裡有沒有沒展開的 `{M}` / `{T}` 模板簡寫。有問題會回報並要求修掉，通過就沒有任何訊息。
   - 用 Bash 腳本批次改檔（不經過 Write / Edit）時 hook 不會觸發，改完要手動跑：`python3 .claude/hooks/check-html.py 檔案.html`。
   - 單獨一個反引號（VS Code 快捷鍵「⌃ `」）是合法的，腳本只抓成對包住文字的。
   - 發現 hook 沒觸發，先檢查 `.claude/settings.json` 和 `.claude/hooks/check-html.py` 還在不在。
   - 錨點 hook 會查，但**重新編號單元時要人工確認文字裡寫的「單元 NN」有跟著改**，那個 hook 抓不到。
2. **每段範例程式碼或指令實際跑一次**，核對「輸出」欄位文字跟終端機印出的一模一樣（包含空格、換行順序），規則見 `references/writing-style.md`。
3. **文字風格自我審查**：對照 `references/writing-style.md` 的贅字清單、抽象包裝詞，能刪就刪、能換成具體術語就換。
4. **and/or 語句加括號**：中文敘述跟程式碼都檢查一次。
5. **有互動輸入的筆記，附錄有「程式卡住怎麼辦」跟「怎麼讀錯誤訊息」嗎**：沒有就補上。
6. **有「要背的只有這幾個」這一塊嗎，而且是不是 5 個以內**：每一項都要是可以直接打出來的形狀，不是知識點；只有 2 個就寫 2 個，不要湊數。規格見 `design-system.md`。
7. **`</body>` 前有沒有 `<script src="annotate.js"></script>`**：選字做筆記的功能靠這一行。檔案在專案根目錄，三份筆記共用。
8. **練習題每一題都有「預期輸出」嗎**：而且是自己跑過的，不是憑印象寫的，涵蓋邊界值，單位跟邊界在題目裡寫死了嗎。
9. 全部確認過，才把檔案交給使用者，並且明講「還沒 commit，要不要 commit」——**不要自己主動 commit 或 push**，除非使用者明確要求。

## 跟使用者的互動習慣

- 修改既有筆記時，用 Edit 針對段落做局部修改，不要整份重寫，方便使用者看出改了哪裡。
- 使用者問到跟執行環境有關的問題（程式沒反應、跳出沒看過的錯誤、編輯器操作），**先確認他是用什麼方式執行的**再回答，不要假設。同一段程式在終端機、Run Cell、Jupyter 裡的行為不一樣，答案也不一樣。
- 學生貼程式碼問對不對，照 `references/review-workflow.md` 的流程走，不要憑讀程式碼判斷結果。
