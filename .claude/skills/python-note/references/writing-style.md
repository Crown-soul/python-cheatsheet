# 文字風格規則（優先度最高，使用者反覆糾正過的重點）

排版怎麼寫在 `design-system.md`，這裡只管文字內容本身。

## 語言與語氣

- 全篇繁體中文，正文口語化、生活化，**不用成語、不用文言文、不用繞口的字**。
- 直接講事實，不用討好、不用客套、不刻意堆好聽話。
- **主要讀者是使用者本人**（還在上課、會回頭複習），同時公開給初學者參考。正文寫法要讓國小高年級學生也看得懂——但這不代表可以不精確，內容還是要百分之百正確，只是用字要白話。
- 比正文更深的原理（為什麼這樣設計、底下發生什麼事）不要硬塞進正文，放進「底下發生什麼事」收合區塊，規則見下方「底層邏輯」。這樣初學者讀正文就夠，使用者想深入再點開。

## 不要用贅字副詞

以下這些字十之八九是填充用的贅字，寫完檢查一次，能刪就刪：**其實、真正、自動（在講「不需要額外動作」之外的語境）、只是、還是（當「仍然」用時）、也就是（當「就是」的贅詞用時）、刻意、基本上、事實上**。

例外：像「才」「只」「就」「永遠」這種**語法上必要**、拿掉會改變意思的字不用刪，例如「才能放在 if 後面」「input() 永遠回傳字串」這種是精確描述，不是贅字。判斷標準：**刪掉這個字，句子的事實內容有沒有改變？沒改變就是贅字，改變了就是必要語法**。

## 讀起來像人寫的：五種不要疊上去的東西

使用者對照過四種語氣，選的是現在這種：平鋪、短句、直接講事實。基本句子不用換，AI 味來自額外疊上去的東西，下面這五種不要寫：

1. **破折號「——」**：想補充就用句號分開，或用「因為」「所以」接起來。
   - ❌ 只有中括號裡的編號在變——這就是迴圈要出場的訊號。
   - ✅ 只有中括號裡的編號在變，這種時候就該用迴圈。
2. **刻意湊成的對句**：照事實寫，不為了工整把兩件事寫成對稱的口號。兩件事本來就是對照關係（and 跟 or），用表格或兩行並列。
   - ❌ = 是動作，== 是問句。
   - ✅ = 把右邊的值存進左邊的變數；== 比較兩邊是否相等，結果是 True 或 False。
3. **安撫讀者的話**：「就好」「沒關係」「不用擔心」「別緊張」。直接講要做的動作，或整句刪掉。
   - ❌ 看不懂沒關係。　❌ 看懂再動手打一次就好。
   - ✅ 看懂之後，自己動手打一次。
   - 例外：「寫 `break` 就好」這種「就好」表示「只需要這樣」，換成「寫 `break`。」一樣清楚，也換掉。
4. **自己發明的比喻、擬人**：「盒子」「貼標籤」「出場的訊號」「range 只記住規則」這類。改成直接描述程式做了什麼。老師上課用過的說法可以留（在筆記裡保留原說法，因為對照上課內容找得到），Python 官方文件自己的用詞也可以。
5. **沒有根據的概括**：「很多人會猜錯」「初學者最常犯」。沒有資料就不寫；有的話講具體來源（「我第一次寫的時候」「批改時出現過」）。

**「我」偶爾出現**：只用在真實經驗，例如 `practice/` 裡寫錯過的程式、批改時錯過的地方。不編造經驗，也不為了口語化硬加。

「一句話重點」目前不套用這五條（使用者決定先不改，因為那是選字筆記最多的地方）；新筆記的一句話重點照這五條寫。

寫完跑 `python3 .claude/skills/python-note/scripts/check-style.py 檔案.html`，它會列出破折號、安撫語、概括說法的位置。對句跟比喻腳本抓不到，要自己讀一遍。

## 不要用抽象包裝去代替現成的具體術語

如果一個概念已經有具體的函式名稱、關鍵字、指令，就直接講那個名字，不要換成模糊的白話包裝。

- ❌「使用者輸入永遠是字串」　✅「input() 回傳的永遠是字串」
- ❌「輸入轉型」　✅「input() 轉型」

判斷標準：如果那個單元的程式碼裡已經明明白白寫著那個函式或指令，標題卻繞著講一個抽象說法，讀者反而要在腦中多轉一手。

## 範例程式的變數命名要守蛇式命名

蛇式命名（全小寫、底線連接）是 Python 筆記單元 03 教的規則，後面所有範例程式的變數名稱都要照做：`student_name`、`set_num`、`other_word`，不要用 `StudentName`、`setNum`、`Other_Word` 這種大寫開頭或駝峰式。唯一例外是刻意示範「全大寫＝常數慣例」的那個單元（`TAX_RATE`、`MAX_SCORE`）。其他科目（例如 Git）沒有這條規則對應的教學單元，就不用套用，但指令、路徑、檔名一樣要用該科目自己的慣例寫清楚，不要自己發明格式。

## and / or：先判斷要不要混用，混用就一定要加括號

兩個條件放在一起之前，先問一句：**這兩個結果會不會同時成立？**

- **會同時成立、各自是獨立的結論**（例如「通過」跟「加分認定」，一個人可以兩個都拿到）：**拆成兩個獨立的 `if`**，不要塞進同一個 `and`/`or` 判斷式，也不要用 `elif`（`elif` 只會執行一個分支，會漏掉本來該同時成立的情況）。
- **是同一個結論的複合條件**（例如某項資格只有「符合」或「不符合」兩種結果）：可以合併寫成一個 `if`，但只要同時出現 `and` 又出現 `or`，**一定要手動加括號**，即使程式語言的優先順序剛好符合你要的邏輯，也要加，讓人一眼看懂，不用去記誰先算。

中文敘述句也是同樣的邏輯：只要同一句話同時出現「而且」「或者」，一定要用引號或頓號把兩個子句物理隔開，不能靠讀者自己猜優先順序。

- ❌「分數 >= 85，或是分數 >= 70 而且出席次數 >= 15」（歧義，看不出括號在哪）
- ✅「分數 >= 85 的人，或是『分數 >= 70 而且出席次數 >= 15』的人」
- 程式碼：`if num >= 85 or (num >= 70 and set_num >= 15):`

## 輸出結果一定要親自驗算，不能憑印象寫

這是最容易出錯、也最容易被使用者抓到的地方。**每一段範例程式碼或終端機指令寫完後，一定要實際執行確認輸出**（Python 用 Bash 跑 `python3`，Git 用 Bash 跑真的 git 指令），不能憑感覺寫「應該是這樣」。特別注意：

1. **程式裡如果有多個 `print()`，或指令連續執行了好幾個，輸出要全部列出來，不能只列最後一步。** 實際發生過的案例：程式碼裡 `input()` 之後緊接著 `print(a)`，會先把輸入值印出來，但筆記寫的「輸出」欄位只列了後面 if/elif 判斷的結果，漏了那行 echo——這種疏漏使用者一定會抓到。
2. **float 運算要注意精度問題**，例如 `0.1 + 0.2` 印出來是 `0.30000000000000004`，不是乾淨的 `0.3`；筆記裡任何牽涉小數的範例，先跑過一次再抄輸出結果。
3. **型別要跟操作對得起來**：`%d` 配字串會炸 `TypeError`，f-string 卻不會擋——這種行為差異如果筆記裡有教到，一定要先實際跑出錯誤訊息再寫進去，不要憑空編錯誤訊息文字。
4. **traceback、terminal 輸出這種多行內容，一字一行照抄實際執行結果**，包含行號、路徑格式、提示字這些細節，不要自己重排或簡化。
5. **Git 指令要在乾淨環境跑**：不然會吃到自己機器的全域設定，寫出來的筆記換一台電腦就不成立。用 `export GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null GIT_AUTHOR_NAME=T GIT_AUTHOR_EMAIL=t@t GIT_COMMITTER_NAME=T GIT_COMMITTER_EMAIL=t@t`。實際發生過的案例：舊備忘錄寫「push 被拒絕就先 `git pull` 再 `git push`」，在沒設 `pull.rebase` 的環境（Git 2.50）`git pull` 會直接 `fatal: Need to specify how to reconcile divergent branches`，要用 `git pull --no-rebase --no-edit`。push 被拒絕就代表兩邊各有新 commit，必然是分岔狀態，所以這個 fatal 一定會遇到。
6. **遠端指令用本機的 `git init --bare` 模擬**（一個 bare 倉庫當 GitHub，兩個 clone 當「本機」和「網頁 / 另一台電腦」），輸出裡的本機路徑換成 `https://github.com/你/demo.git`。因為不是終端機，上傳下載的進度行（`Enumerating objects…`）不會出現，筆記要註明「畫面上還有幾行進度，跟成功與否無關，這裡省略」。
7. **會開編輯器的指令要處理**：`git commit`（沒加 `-m`）、`git revert`、`git pull` 產生合併 commit 時 Git 會開 vim，初學者會卡住。範例一律加 `-m` 或 `--no-edit`，並在附錄「指令卡住了怎麼辦」講怎麼離開。`git log`、`git diff` 輸出太長會停在分頁畫面，按 `q` 離開，也寫進同一個附錄。

## 效能的說法一律實測，不要照抄任何人的講法

筆記裡只要出現「A 比 B 快」這種句子，**一定要用 `timeit` 實際量過再寫**，不管這句話是老師講的、使用者寫在筆記裡的，還是網路教材寫的。這類說法錯得特別多，而且照抄會直接教錯。

實際遇過的三個案例，全部不成立：

| 原本的說法 | 實測結果 |
|---|---|
| 「`i++`、`i += 1`、`i = i + 1` 由快到慢」（抄自 C 家族習慣） | Python 根本沒有 `i++`（`SyntaxError`）；另外兩個一百萬次各約 0.063 秒，**沒有差別** |
| 「Python 自己的函式就比較快」 | 自己寫的 `def` 不會比較快。快的是**內建函式**（`sum(range(...))` 比手寫迴圈快約 2.5 倍） |
| 「`enumerate` 比手動 `i += 1` 快」 | 一百萬筆 25.5 ms 對 25.2 ms，**沒有差別**。`enumerate` 的好處是少寫三行、少一個會縮排放錯的地方，不是速度 |

寫法規則：

- 量測數字要寫進筆記（「一百萬筆實測 30 毫秒 對 12 毫秒」），不要只寫「比較快」。
- 沒差的就明講沒差，並且說出真正的好處是什麼（可讀性、不容易寫錯）。
- 分不清「自訂函式」跟「內建函式」是這類錯誤的常見來源，筆記裡要用詞精確。
- 教學單元仍然用手寫迴圈的版本（要教的是迴圈怎麼運作），內建寫法用一句「進階補充」帶過就好。

## 底層邏輯：「底下發生什麼事」區塊

使用者現階段的目標是打好基礎跟底層邏輯，所以筆記除了「怎麼寫」，還要有地方看「為什麼」。

- **放什麼**：這個語法底下發生什麼事、為什麼 Python 要這樣設計。例如：變數名稱指向記憶體裡的一份資料（`a = b` 之後兩個名字指向同一份）、`range` 只記住規則不存數字、`input()` 為什麼永遠回傳字串。
- **什麼時候放**：只放在「不懂底層就會踩坑」或「懂了之後能少背很多規則」的單元。不是每個單元都要有，一份筆記大概 3～6 個。
- **直接描述，再用程式證明**：不用比喻（規則見「讀起來像人寫的」），直接講底下發生什麼事，接一段實際跑過的程式（`id()`、`type()`、`is`、`sys.getsizeof()`），讓讀者自己看到證據。證明程式的輸出一樣要一字不漏照抄實際結果。
- **跟「容易踩的坑」的分工**：坑講「會出什麼錯」，這個區塊講「為什麼會出這個錯」。兩者講同一件事時，坑的文字保持短，原因留在這個區塊，不要重複寫兩次。
- 排版見 `design-system.md`「底下發生什麼事」。

## 延伸應用：「之後能拿來做什麼」區塊

使用者還不確定之後要用 Python 做什麼，這個區塊讓使用者先看到每個觀念在真實用途裡長什麼樣子。

- **只放在有明顯應用的單元**。舉不出具體、真實的用途就不放，不要硬湊（例如「變數命名規則」就沒有需要放的延伸應用）。
- **方向照優先順序**：資料分析 → 小工具 → 網頁 API。一個單元最多寫兩個方向，優先挑前面的。
- **要具體到一個動作**：❌「迴圈在資料分析很常用」　✅「一份 CSV 有 300 列成績，用 for 一列一列讀，算出全班平均」。
- **範例程式可有可無**，有的話不超過 8 行，而且一樣要實際跑過。用到還沒教的語法或套件（`pandas`、`requests`），在區塊裡標「這段先認得形狀，路線圖第 N 站會教」，不要求讀者看懂。
- 排版見 `design-system.md`「之後能拿來做什麼」。

## 程式好像卡住了怎麼辦（附錄的必要區塊）

實際帶初學者的經驗：**卡在「程式跑不起來」或「指令沒反應」的時間，遠多於卡在語法/指令本身的時間**，而且這種卡關最容易讓人放棄，因為看起來完全沒有線索。筆記如果只教語法、不教怎麼把東西跑起來，學生會卡在一個筆記完全沒提到的地方。

只要筆記裡有互動式的程式或指令，附錄就要有這一塊，至少涵蓋（依科目實際會遇到的狀況調整）：

- 症狀：使用者實際會看到什麼（畫面沒反應、跳出沒看過的訊息、游標在閃）
- 真正的原因：不是語法錯，是操作或環境問題
- 怎麼處理：具體動作，不要寫「請檢查環境設定」這種沒有動作的話

Python 筆記目前的三個真實案例：VS Code Run Cell 的 `input()` 輸入框跳在編輯器最上方、`KeyboardInterrupt` 是有人按了 Ctrl+C（常見原因是想複製終端機文字卻按錯鍵）、游標閃爍是正常在等輸入。新科目遇到同類狀況要照這個格式補進去，不要略過。

## 怎麼讀錯誤訊息（附錄的必要區塊）

只要筆記裡有任何一個單元會讓初學者跑出錯誤或非預期結果，附錄就要教「怎麼找問題」，不只是「這個詞是什麼意思」。至少要教：

1. **從最後一行（或最後的結果）看起**：那裡通常就是結論。
2. **有沒有指出問題在哪裡**（行號、指令、哪個步驟）：直接跳過去，不用從頭找。
3. **中間的細節哪些可以先跳過**：降低初學者被一長串輸出嚇到的機率。

範例一定要是**實際執行出來**的內容，不要自己編。

## 「學完這份你能做到」與「自我檢核清單」

這兩塊是同一組內容的頭尾：開頭先講這份筆記要讓你能做到什麼，結尾逐條確認有沒有做到。

- **開頭 3～5 條**，每條都是**看得到結果的動作**，動詞開頭：✅「用 for 跟 range 印出九九乘法表」　❌「理解迴圈的概念」（「理解」「熟悉」「掌握」無法檢查，不准用）。
- **結尾的自我檢核清單，逐條對應開頭那幾條**，改寫成「不看筆記，能不能……」的問句，每條後面附「做不到 → 回單元 NN」。條數跟開頭一樣，不要多加。
- **跟另外兩個清單的分工**，三者不要重複：

| 區塊 | 位置 | 內容 | 時機 |
|---|---|---|---|
| 要背的只有這幾個 | 開頭 | 打得出來的**語法形狀** | 動手打之前 |
| 寫完自己檢查一遍（附錄） | 附錄 | 寫完程式要核對的**坑** | 每寫完一段程式 |
| 自我檢核清單 | 最後 | 開頭列的**能力**有沒有做到 | 整份讀完、練習寫完 |

## 練習題

**每份筆記預設都要附練習題，不附答案。** 使用者明確說要答案，才用「參考解答」元件補上（規則見 `design-system.md`）。

### 三種題型

一份筆記的練習題要混用這三種，不要全部同一種：

| 題型 | 考什麼 | 題目給什麼 | 怎麼知道自己對了 |
|---|---|---|---|
| **預測輸出** | 看得懂程式在做什麼 | 一段完整程式，**不給輸出** | 先寫下猜測，再貼進編輯器執行對照——執行結果就是答案 |
| **找錯改錯** | 認得出常見的錯 | 一段有 bug 的程式 + 題目本來要它做什麼 + 它實際跑出來的（錯誤）結果 | 附「預期輸出」，改完跑出來一樣就對了 |
| **寫寫看** | 自己寫得出來 | 需求描述 | 附「預期輸出」 |

- **預測輸出**題的程式，出題的人一樣要實際跑過，確認輸出是自己想考的那個（不要本來想考迴圈次數，結果程式在第二行就報錯）。故意考「會報錯」的題目可以，但題目要寫「如果會出錯，猜是哪一種錯誤」。
- **找錯改錯**題的素材來源有優先順序，見 `source-material.md`「找錯改錯題的素材」。題目裡的「實際結果」要真的跑出來貼上，**不要指出錯在哪一行**，那就是答案。一題只藏一個錯，除非題目明講「有兩個錯」。
- **寫寫看**：下面「預期輸出」的規則全部適用。

### 小專案與跨章專案

- **每份筆記結尾一個小專案**（舊版筆記裡叫「大魔王」，不用改名）：把這份筆記教的東西串成一個**能拿來用的小程式**，不是單純的綜合題。例如「記帳：輸入 5 筆花費，印出總和跟最大的一筆」，不是「用到 for、if、range 的題目」。
- **跨章專案**：大約每 2～4 份筆記做一個，獨立一頁，只能用到路線圖上排在它前面的觀念。題目先跟使用者確認，規格見 `roadmap.md` 跟 `design-system.md`「跨章專案頁」。
- 兩種專案都要分步驟（先做最小能跑的版本，再一步步加功能），都要附預期輸出。

### 預期輸出（預測輸出題以外，每一題都要附）

- 預測輸出題不附，因為輸出本身就是答案，讀者執行一次就能對照。
- **不附解答，但一定要附一組具體的輸入對應的正確輸出（「預期輸出」）**。不給答案的用意是讓學生自己想，但如果連「怎麼知道自己寫對了」都沒有，學生寫完只能去問人，等於還是沒辦法自己走完一題。
- 給的是**驗證依據**（輸入 60，畫面應該出現 63.0），不是**解法**（不要寫出算式或指令本身）。
- 實際發生過的案例：練習題「一杯咖啡原價 60 元，稅率 5%，算出含稅價格」，學生寫成 `price * (1 - TAX)`，算出 57.0，程式能跑、不會報錯，所以完全沒發現算反了。題目旁邊如果有「輸入 60 → 63.0」，他自己就抓到了。
- 有多個分支的題目，至少給 2～3 組涵蓋不同分支的輸入輸出，包含邊界值。
- 這組預期輸出，**自己要先實際執行過**，不能憑印象寫。
- **單位跟邊界要在題目裡寫死**：單位要跟程式或指令裡用的數字對得起來（實際案例：題目說身高用公分，學生的程式卻問「Enter your height in m」，拿小數去跟三位數比，永遠不成立）；「幾以上」這種模糊講法要明講是 `>=` 還是 `>`，邊界值要出現在預期輸出裡。
